# codex-implement

Codex に実装を委譲する。**ワーキングツリーを直接書き換える。**
レビューや相談だけなら `codex-review` を使う。

## 実行前チェック（必須）

1. **`git status` がクリーンであること。** 未コミットの変更は先にコミットするか退避する。
   汚れたまま委譲すると、Codex の変更と自分の変更が混ざって切り分けられなくなる
2. **既定ブランチに直接コミットしない。** 作業ブランチを切ってから委譲する
3. **依頼は 1 つの目的に絞る。** 無関係な変更を同時に投げない
4. **並行実行するなら worktree を用意する**（後述）

## 実行

```bash
output_file="$(mktemp "${TMPDIR:-/tmp}/codex-implement.XXXXXX")"
codex exec --sandbox workspace-write -C <project_dir> -o "$output_file" < /path/to/prompt.md
printf 'Codex output: %s\n' "$output_file"
```

`output_file` は実行ごとに新しく作る。並行実行時も同じ出力先を共有しない。

多段階・長時間になりそうなものは Claude Code のバックグラウンド実行に載せる。待つ間は
**ワーキングツリーを触らない**。触ると衝突する。

### 追い込み

同じセッションを継続する。前提が引き継がれるので、context を書き直す必要がない。

```bash
output_file="$(mktemp "${TMPDIR:-/tmp}/codex-implement.XXXXXX")"
codex exec --sandbox workspace-write resume --last -o "$output_file" - < /path/to/followup.md
printf 'Codex output: %s\n' "$output_file"
```

### 実行の作法

**プロンプトはファイルに書いて渡す。** 引用符・バックティック・改行がシェルで壊れる。
スクラッチパッドに `.md` で書き、`< file` で流し込む。

**最終回答は `-o <file>` で受け取る。** stdout には実行ログ・reasoning・MCP のエラーが混ざり、
100KB を超えることがある。読むのは `-o` で指定したファイル。

### サンドボックスエラー時

まず上のコマンドのまま実行する。次のエラーが出たら自動で再実行せず停止する。

```
sandbox-exec: sandbox_apply: Operation not permitted
```

Codex が自前の Seatbelt サンドボックスを張れなかった、という意味。このエラーだけでは、外側に
十分なサンドボックスがあるとは判断できない。

1. 利用者にエラーを報告する
2. `danger-full-access` では Codex 側のファイルアクセス制限がなくなり、保護は実行環境の外側の
   サンドボックスに依存することを説明する
3. **利用者の明示的な許可を得た場合だけ**、次のコマンドで再実行する

```bash
output_file="$(mktemp "${TMPDIR:-/tmp}/codex-implement.XXXXXX")"
codex exec --sandbox danger-full-access -C <project_dir> -o "$output_file" < /path/to/prompt.md
printf 'Codex output: %s\n' "$output_file"
```

許可を得る前に実行しない。最初から `danger-full-access` を使わない。

### `apply_patch` の失敗は無視してよい

`workspace-write` で走らせると、Codex の `apply_patch` が Seatbelt 制約で失敗することがある。
Codex は自力で `git apply` にフォールバックする。**差分が適用されていれば問題ない。**
`git diff` で結果を確認すればよく、この失敗自体を追う必要はない。

## ブランチか worktree か

**ブランチだけでは並行実行できない。** `codex exec --cd <dir>` が書き換えるのはそのディレクトリの
ワーキングツリーで、ブランチは単なるポインタ。同じリポジトリで 2 本走らせれば同じファイルと index を
取り合う。バックグラウンド実行中に自分が別作業をするのも同じ衝突。

| やり方 | 必要な隔離 |
|---|---|
| 逐次実行（1 本ずつ、待つ間はツリーを触らない） | 作業ブランチで十分 |
| 並行実行、または実行中に別作業 | worktree 必須 |

既定は作業ブランチ。worktree は並行させたいときだけ使う。
**新しい worktree には `node_modules` 等の依存が無いため、事後検証のテストと型チェックがそのままでは
回らない。** インストールの時間が乗ることを織り込んで選ぶ。

作り方は用途で分ける。

- `EnterWorktree` … セッション自体を worktree に移す。自分がそこで作業するとき
- `git worktree add` … ディレクトリだけ用意する。Codex を複数並行させるときはこちら。
  `codex exec -C <各worktree>` で振り分ける

## 事後検証（省略不可）

**Codex の出力をそのまま成果として報告してはならない。** 必ず次を行う。

1. **`git diff` を読み、変更内容を自分で理解する。** 読まずに報告しない
2. **テストと型チェックを実行し、結果を確認する。** プロジェクトのコマンドを使う
3. **妥当でない変更・過剰な変更は差し戻すか修正する。** Codex の提案を無批判に受け入れない。
   依頼範囲を超えた変更が混ざっていないかを特に見る
4. **報告で、どこを Codex が書きどこを自分が書いたかを明示する**
5. **テストが落ちている、型エラーが残っている場合はその事実を隠さず報告する**

## プロンプトに必ず含めるもの

- 対象リポジトリ、ブランチ、ワーキングツリーの状態
- 守るべき制約（振る舞いを変えない範囲、触ってよいファイル、既存テストを削除・弱体化しない）
- 実行してほしい検証コマンドと、この環境で動かないものの但し書き
  （動かないものを事前に伝えないと、Codex が自分の変更のせいだと誤認して迷走する）
- 報告してほしい内容（何を変えたか、判断の理由、実行した検証と結果、落ちたものがあれば隠さず）
- 「コミットはしないこと。ワーキングツリーに変更を残すだけでよい」
- 「確認や質問は不要です。具体的な提案・修正案・コード例まで自主的に出力してください」
  （`codex exec` は非対話。質問を返されると往復が丸ごと無駄になる）
- 変えない結論も歓迎する旨（「簡潔にならないなら変えないこと」など）。
  これが無いと、変える必要のない箇所まで触ってくる

## モデルと Effort

決めるのは呼び出し側。このスキルは受け取って渡すだけで、固定値を持たない。

| 項目 | 渡し方 | 既定 |
|---|---|---|
| モデル | `-m <model>` | 指定なし（Codex 側の設定に従う） |
| Effort | `-c model_reasoning_effort="<値>"` | 指定なし |

`codex exec` に `--effort` フラグは無い。config override 経由が正しい。
値は `none` / `minimal` / `low` / `medium` / `high` / `xhigh`。

| 状況 | Effort |
|---|---|
| 小さい確認、定型作業、既存パターンの踏襲 | `low` |
| 通常の実装 | 指定なし |
| 2 回試して直らないバグ、設計判断、横断的なリファクタリング | `high` |
| 上記でも詰まったとき、再挑戦時 | `xhigh` |

再挑戦時は 1 段上げる。同じ Effort で投げ直しても同じところで詰まる。
