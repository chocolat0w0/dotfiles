# Session Friction Log

セッション中の摩擦（ユーザーによる軌道修正、前提や範囲の認識違い、不要な手戻り）を
記録し、同じ原因が 3 セッションで再発したときに恒久対応を提案する。

**ユーザーが明示的に依頼したときだけ起動する。** 通常作業中に勝手に振り返りや記録を
始めない。

## 共有ログ

プロジェクトルートの `docs/agent-friction-log.md` が Claude と Codex の共有ログである。
このファイルを唯一の永続データとして扱う。スキルのインストール元・エージェントの
個人設定・会話履歴の保存先へ、ログを書き込まない。

書式、カテゴリ、状態、回数の定義は [log-format.md](references/log-format.md) に従う。
ログを更新する前に必ず読む。

## Evidence

利用中のエージェントがアクセスできる根拠だけを使う。現セッションでは会話、実行結果、
ユーザーの軌道修正、ツール失敗を確認する。見えない履歴を推測で補わない。

過去の会話エクスポートを読む方法はエージェントごとに異なる。Claude Code の過去
transcript を対象にするときだけ、このスキルに同梱された Claude 専用抽出器
`extract_claude_friction.py` を使える。インストール済みスキルディレクトリから次の形で
実行する。

```bash
python3 <installed-skill-dir>/scripts/extract_claude_friction.py --cwd <project-root>
python3 <installed-skill-dir>/scripts/extract_claude_friction.py --list --cwd <project-root>
python3 <installed-skill-dir>/scripts/extract_claude_friction.py --session <id> --cwd <project-root>
```

Codex を含め、抽出器が利用できない環境では、現在見えている会話とユーザーが示した資料を
根拠にする。抽出器が使えないこと自体を摩擦として記録しない。

抽出器のイベントは候補にすぎない。すべての `user-prompt` が摩擦とは限らず、候補にない
事実を補うには会話の前後を確認する。任意のレビュー環境では、フィードバックがツール結果
に現れることがある。その環境を使っている場合だけ、その結果も根拠として読む。

## Workflow

### 1. 対象を確定する

現セッションか、ユーザーが指定した過去セッションかを確定する。過去セッションで
エクスポートを利用できない場合は、その制約を伝え、ユーザーが提示した情報だけで
振り返るかを確認する。

### 2. 摩擦を判定して分類する

次を摩擦候補として判定する。

- ユーザーがやり直し、方針変更、範囲訂正を求めた
- 依頼の前提または範囲を取り違えた
- 確認すべき点を推測で進めた、または判断して進めるべき場面で止まった
- 環境、ツール、プロジェクト規約の前提を誤り、手戻りした
- ツール拒否、中断、継続阻止を受けた

通常の追加依頼、情報追加による自然な仕様変更、一度で解消した軽微な入力ミス、短い相槌は
摩擦に含めない。

[log-format.md](references/log-format.md) の A〜F に分類する。迷った場合は、余分な作業が
生じた問題を E、成果物や報告の伝わり方の問題を F とする。新しいカテゴリは作らない。

### 3. 同じ原因を一つのエントリに束ねる

表面的な症状ではなく原因が同じかで、既存エントリへの再発記録か新規記録かを決める。
判断に迷ったら「その対処をしていれば、これも防げたか」を問う。防げるなら同一、
防げないなら別エントリとする。

新しい事例が既存エントリより広い原因を示すなら、既存の見出しと内容を広い概念へ
書き換えて統合し、ID は維持する。分割は、対処が明確に異なる場合だけにする。

### 4. 共有ログを更新する

- 新規エントリには `F-` + 次の連番を付ける。
- 再発は、対象セッション ID が既存の `記録セッション` にないときだけ回数を 1 増やし、
  対象セッションの日付を追記する。
- `集計済みセッション` には、摩擦が 0 件でも対象セッションを追記する。
- サマリ表は全エントリから再作成し、ID 昇順にする。

更新後、何を記録したかを簡潔に伝える。ログへの事実の記録には追加承認を求めない。
コミットはしない。

### 5. 恒久対応が必要かを判定する

`発生回数` が 3 以上で、状態が `未対処` または `暫定対処` の項目だけを対象にする。
`恒久対応済み` と `恒久対応見送り` は再提案しない。該当がなければ、その旨を伝えて
終了する。

### 6. 恒久対応を提案し、承認後に適用する

次のセッションのエージェントが判断できる場所へ、具体的な対応を置く。

| 対応先 | 向いているもの |
| --- | --- |
| プロジェクトの instruction | プロジェクト全体または特定領域の規約・前提 |
| 既存スキル | そのスキルの手順の穴 |
| 新規スキル | 独立した反復手順 |
| dotfiles | 複数プロジェクト・複数エージェントへ配布する作法 |
| 利用中エージェントの設定 | フックや権限など、機構で防げるもの |

実装から読める事実は規約に重ね書きしない。実装だけでは読めない判断基準、前提、経緯を
記述する。具体案を示し、ユーザーが承認したものだけ適用する。却下なら
`恒久対応見送り` と理由を記録し、無回答なら状態を変えない。

## 注意

- 記録は次のエージェントへの申し送りであり、ユーザーを非難しない。行動を変えられる側の
  前提や手順として書く。
- 過去セッションの一括棚卸しは、ユーザーが明示的に依頼した場合だけ行う。
- ログが 30 エントリを超えて読みにくくなったら、古い `恒久対応済み` 項目のアーカイブを
  ユーザーへ提案する。削除はしない。
